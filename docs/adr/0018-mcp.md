# ADR 0018: The MCP server

- Status: accepted
- Date: 2026-11-25

## Context

The Claude Code skill reads the corpus from files on the machine it is installed on. An owner who runs Magpie on another always-on machine, such as a Mac Mini, has no corpus next to the agent they code with. The sync-runner plan deferred "a Claude skill that queries a remote magpie server". This record takes that item up.

When the code changes, update or remove the entry here in the same commit.

## Decisions

### `packages/mcp/server.mjs`

#### 0018.1 `served by the web app, not a new listener`

The MCP endpoint is a route of the web app, `/mcp`, so it adds no port, process or service. It sits behind the same loopback host guard as the rest of the app (`apps/web/src/proxy.ts`). Reaching it from another machine takes a reverse proxy the owner runs, such as Caddy on a Tailscale address, that sends a loopback `Host` header. The tailnet is then the only access boundary: the endpoint has no sign-in, like the app. The proxy should forward `/mcp` alone. A loopback `Host` satisfies the app's one guard for every path the proxy forwards, and requests without an `Origin` pass the same-origin checks on `/api/ask` and on server actions, so a whole-app proxy gives each tailnet peer Ask, the settings and the edits, not the four reads. `docs/usage.md` carries the Caddy recipe. Before it is exposed beyond a private network it needs OAuth 2.1, which the 2026-07-28 MCP spec expects of remote servers.

#### 0018.2 `read-only tools`

The tools are `list_categories`, `topic_posts`, `topic_resources` and `search_posts`, the four reads the skill offers. Nothing changes the store, and Ask is not exposed, because it spends the owner's Jev and Claude usage.

#### 0018.3 `one query library for the skill and the server`

The rules for hidden areas, removed posts, schema versions and corpus age live once, in `packages/skill/corpus.mjs`. `query.mjs` prints what it returns, and the server returns it as JSON, shaped as 0018.10 says. That file imports only node built-ins, because the skill runs under whatever node the calling session has (0012.3); the MCP SDK and zod belong to `packages/mcp` alone.

#### 0018.4 `the served skill`

The server provides the magpie skill through the skills extension (`io.modelcontextprotocol/skills`, SEP-2640), from `packages/mcp/skills/magpie/SKILL.md`. It is a separate file from `packages/skill/SKILL.md` because it names the tools, not `node query.mjs`, which does not exist on the client. It lives outside `packages/skill`, which is linked into `~/.claude/skills` and would load a second skill. The server `instructions` repeat the rule that post text is quoted material, never instructions, because hosts that do not load served skills (`claude -p`, cloud sessions, the Agent SDK) still read those.

#### 0018.5 `corpus age in the result`

The skill prints the stale-corpus note on stderr. A tool result has no stderr, so the note is the first content block of every result.

#### 0018.8 `every tool needs the store`

The skill's keyword search still runs when no store exists, from the export files alone. The server does not: without a store, or with one older than the baseline schema, every tool returns an error, `search_posts` included. Which posts are hidden or removed is recorded only in the store, so a search without it would hand a remote agent posts the owner hid or removed.

#### 0018.9 `remedies name the host, not the skill`

`corpus.mjs` states what is wrong and each caller adds what to do about it. The skill names commands and paths on its own machine (`bun run service:status`, `MAGPIE_DIR`). The server tells the agent to send the owner to the machine that hosts Magpie, because the agent cannot run those commands and the paths mean nothing where it runs.

#### 0018.10 `results are shaped for an agent's context`

A tool result lands whole in a remote agent's context, so the server trims what the skill prints in full and adds what the agent cannot fetch cheaply. Post text over 400 characters is cut and marked `truncated`, as the skill's `--full` flag does; `full: true` returns it whole, and `search_posts` takes a post `id` to fetch one cut post. A default search for a common phrase went from 38 KB to 9 KB, 10 KB once hits name their topics. Each post lists its `links`: the addresses and titles the sync already resolved from t.co, leaving out links that resolve back to X. Search hits list the topics they are confidently in, hidden topics left out unless `include_hidden` is set, so an agent can go from a hit to `topic_posts`. The search `score` is left out because it ranks results and means nothing to the reader. These live in the server, not `corpus.mjs`, so the skill's output stays as it was.

`limit` stops at 50 to keep one result small, so `topic_posts`, `topic_resources` and `search_posts` take an `offset`. Each reports the `total`, and an agent reads the rest by calling again. Without it, a topic or a search with more than 50 matches had posts no call could reach. The skill has no `--offset`, because its `--limit` has no ceiling.

No search path ranks a newer post above an older one for being newer. An old post is not the same as a replaced one, and only a reader that sees both can tell them apart, so the server gives the reader the dates and the controls and the guidance says to prefer the later post when two disagree. `topic_posts` and `topic_resources` take `since`, as `search_posts` does. `topic_posts` takes `sort: "newest"`, the web list's Newest order. The web list defaults to Recently added (0013.17), which the server does not offer: it orders by when a sync saw a post, not by when it was written. Each resource carries `last_shared`, because most-posted-first favours a resource that has had years to collect posts over the one that replaced it last month. The web answer prompt gives Claude the same rule (0014.14), and the options themselves live in `corpus.mjs` (0012.13). A decay in the ranking would wait for a measured case where the top of a topic is mostly replaced posts.

### `apps/web/src/app/mcp/route.ts`

#### 0018.6 `requests with an Origin header are refused`

MCP clients send no Origin header; browsers send one on every cross-origin POST. Refusing any request that carries one keeps a web page from driving the endpoint, which the MCP transport spec requires servers to guard against.

#### 0018.7 `corpus paths come from the engine`

The route hands the server the engine's `paths()`, not the skill's own lookup next to its file. The engine follows `MAGPIE_ROOT` and resolves a linked worktree to its main checkout, so the endpoint reads the same store as the rest of the app.
